# entire-agent-aider — protocol mapping and verified aider behaviour

Every claim here was read out of aider 0.86.2's installed source, not its
documentation, and the parser is tested against `internal/aider/testdata/chat_history.md`
— a fixture generated by driving aider's own `InputOutput` writer, so it is
byte-for-byte what aider produces rather than a hand-written mock.

## Why this agent is shaped differently from the others

Aider has no hook or plugin system. It exposes exactly one outbound callback,
and that callback is far weaker than it looks:

```python
# aider/io.py:1088
def ring_bell(self):
    if self.bell_on_next_input and self.notifications:
        if self.notifications_command:
            result = subprocess.run(
                self.notifications_command, shell=True, capture_output=True
            )
            if result.returncode != 0 and result.stderr:
                self.tool_warning(f"Failed to run notifications command: {error_msg}")
        ...
        self.bell_on_next_input = False
```

Five consequences drive the whole design:

1. **`notifications: true` is mandatory.** The guard requires it. Setting only
   `notifications-command` is a silent no-op that captures nothing.
2. **No argv, no environment, no stdin.** Session identity cannot be passed in,
   so it is derived from the transcript instead.
3. **stdout/stderr are discarded** (`capture_output=True`).
4. **A non-zero exit is shown to the user** on every affected turn. `parse-hook`
   therefore never returns an error — an uninterpretable turn-end is reported as
   `null`, which is the protocol's "nothing happened".
5. **It is not a turn-end signal.** `ring_bell()` is reached from `get_input()`,
   `confirm_ask()` and `prompt_ask()` — all interactive-input paths. It fires
   mid-turn whenever a confirmation prompt appears, and never at all under
   `aider -m ... --yes-always`.

## Hook installation

`install-hooks` writes a marked block into `.aider.conf.yml` at the repo root.
Aider parses that file with `configargparse` and includes the git-root copy in
`default_config_files` (`main.py:474-475`), so a plain `aider` run picks it all
up with no wrapper:

```yaml
# >>> entire-agent-aider (managed) >>>
notifications: true
notifications-command: "echo {} | entire hooks aider turn-end"
chat-history-file: .entire/aider/chat.md
llm-history-file: .entire/aider/llm.log
input-history-file: .entire/aider/input.history
# <<< entire-agent-aider (managed) <<<
```

Content outside the markers is never touched, and `uninstall-hooks` restores the
file exactly (removing it only if it held nothing else).

**The `echo {}` is load-bearing.** Entire's external-agent bridge reads the hook
payload from stdin before the plugin runs and rejects an empty read with
`parse-hook: read stdin: empty hook input`. Since aider passes no stdin, that
would surface as a warning in the user's session every turn. `echo {} | ...` is
valid in both POSIX `sh` and `cmd.exe` and needs no path quoting.

Redirecting the history files into `.entire/` also keeps the working tree clean.
Entire's strategy layer already treats everything under `.entire` as protected,
so transcripts never enter a checkpoint as file changes.

## Transcript format

| Writer | Source | Output |
|---|---|---|
| Session banner | io.py:336 | `# aider chat started at {time}` |
| **User prompt** | `user_input()` io.py:775 | `#### {line}` — on **every** line |
| **Assistant output** | `ai_output()` io.py:794 | unmarked prose |
| Tool output, warnings, confirm answers | `_tool_message()` io.py:965+ | `> {line}` |

Two traps this parser handles, both of which silently corrupt naive parsers:

- **A multi-line prompt is one turn.** `user_input` prefixes every line, so a
  two-line submission produces two `#### ` lines. Turns therefore open at a *run*
  of consecutive prefixed lines. The test fixture has 5 `####` lines and 4 turns.
- **Line endings are platform-native.** Aider defaults to
  `line_endings="platform"`, so the same file is CRLF on Windows and LF
  elsewhere. Classification always runs against a `\r`-trimmed copy while the
  original bytes are preserved for storage.

## Session identity

Aider records no session ID. The banner it writes at startup is the only per-run
marker in the file, so its timestamp becomes the ID, normalized to
`YYYYMMDD-HHMMSS` (no colons — Entire rejects the Windows volume separator in a
value used as a path component).

One consequence, stated plainly: because aider is configured through a static
YAML file with a single `chat-history-file`, every run in a repo appends to the
same transcript. Runs are separated by the banner inside it, not by separate
files.

## Turn-end dedup

`parse-hook --hook turn-end` compares a fingerprint of the newest turn against
`.entire/aider/state.json`:

```
{turn index, usage-report count, applied-edit count}
```

An event is emitted only when that fingerprint advances. This is required, not
defensive, because of consequence 5 above, and the ordering inside
`Coder.send_message` is what makes a bare turn index insufficient:

```
base_coder.py:1423  llm_started()        -> arms the bell
base_coder.py:1531  show_usage_report()  -> writes "> Tokens: ..."
base_coder.py:1585  apply_updates()      -> writes "> Applied edit to ..."
base_coder.py:1589  auto_commit()        -> git commit
```

A confirmation prompt inside `apply_updates` rings the bell after the usage
report but **before** the commit; a turn needing no confirmation rings it at
`get_input()` after everything. A turn with neither a usage report nor an applied
edit is treated as "nothing observable happened" and produces no checkpoint.

## File modifications

Taken from aider's own `Applied edit to <path>` line, emitted per path by
`Coder.apply_updates` (`base_coder.py:2334`) **only after the edit lands**.
Scraping the SEARCH/REPLACE blocks out of the assistant prose would also pick up
edits that failed to apply.

## Token accounting — and its limit

Parsed from aider's usage report, which reaches the chat history as
`> Tokens: 15k sent, 1.1k cache write, 3.2k cache hit, 642 received. Cost: ...`

Reports are **independent, not cumulative**: `show_usage_report` zeroes the
per-message counters immediately after emitting each line
(`base_coder.py:2124-2126`), so several reports inside one turn — what a lint or
test reflection loop produces — are summed.

**Counts are lossy above 999 and no unrounded copy exists anywhere on disk.**
`format_tokens` (`utils.py:276`) renders `<1000` exactly, `<10000` as `1.2k`, and
everything else as `15k`; `--llm-history-file` carries full request/response text
but no counts at all. Token metadata for aider sessions is therefore exact below
1000 and rounded above it. This is reported as-is rather than presented as
precise.

## Protected paths

`.aider.tags.cache.v3` **and** `.aider.tags.cache.v4` are both declared: the
suffix is decided at import time by whether `tree-sitter-language-pack` is
installed (`repomap.py:33-43`), so two installs of the same aider release can
disagree, and matching is exact per path component.

Aider's default history paths are declared in `protected_files` even though
`install-hooks` redirects them, so a user running aider with its stock config
still cannot push a chat log into a checkpoint.

## Known limitations

- **No `TurnStart`.** Aider has no pre-prompt callback of any kind, so Entire
  cannot capture state before a prompt is submitted. Checkpoints are created at
  turn end only.
- **Headless `aider -m ...` is not captured.** `ring_bell` is unreachable
  without an interactive prompt, so no notification ever fires.
- **Token counts are rounded above 1000** — see above.
- **Resume is file-scoped, not run-scoped.** `aider --restore-chat-history`
  replays whatever the configured `chat-history-file` holds; aider has no flag
  that selects one run.
